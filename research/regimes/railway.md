# Railway — pricing regimes (as of 2026-09-28)
Railway is a usage-metered PaaS with **two separate compute rate cards**: container rates for normal services and **VM rates (2.5x CPU, 5x RAM)** for anything on its VM primitive (Sandboxes, Cloud Agents, the no-account free VM). All usage, container or VM, draws down the same plan credit. The plan fee is a minimum spend that is credited against usage. Committed-spend tiers work the same way at larger sizes.

## Gotchas
- **VM RAM costs 5x container RAM, and the page cache counts.** A sandbox that `git clone`s and builds a big repo fills the page cache, so billed RAM trends toward the allocation even at low CPU. RAM ends up 80–90% of a sandbox bill.
- **The marketing page and the docs contradict each other.** The pricing page says sandboxes are "never [billed] for the time it spends waiting". The docs say "memory remains billable while a VM waits for work". Trust the docs: waiting is cheap on CPU but not on RAM.
- **Idle timeout destroys; it does not pause.** Every forgotten sandbox bills up to 30 min of resident RAM by default, and it never stops if `idleTimeoutMinutes=0`. Forks don't inherit the timeout.
- **Cloud Agents have no idle timeout.** They bill until you explicitly sleep them.
- **Checkpoint storage has no published price.** The only published limit is on count (10/50/100 per environment).
- Sandbox concurrency is **per environment**, so more environments means more concurrency.
- **Committed spend is not a discount.** It is a minimum that unlocks compliance and dedicated hardware (HIPAA needs $1k/mo plus a 1-yr term).
- Hobby max sandbox is 8 vCPU/8 GB with 50 concurrent. That exactly fits the worked example, so there is no need to pay for Pro.
- The usage "hard limit" takes **all workloads offline**. Agent Usage limits cover only the Railway Agent's LLM spend, not sandboxes.
